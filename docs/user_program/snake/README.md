# 终端贪吃蛇

源码与游戏规则均位于 [snake.c](../../../user-programs/programs/snake/snake.c)。
这是用户态实时交互示例，使用键盘硬中断回调、毫秒时间系统调用、批量终端输出。
不访问设备 MMIO，不执行 DI/EI/HALT，不改变现有 tick 调度。

## 运行与操作

项目根目录执行：

```powershell
.\build-tools\build.ps1 -Program snake
```

将 `kernel/build/kernel.hex` 加载到内核 ROM，将
`user-programs/programs/snake/build/snake.hex` 加载到 UROM，然后复位。
**必须使用配套的新内核**：新增 Write/TimeMs 系统调用，且 INT 的实际 ROM 地址发生了变化。
不要只换用户 HEX、继续使用旧内核。

| 按键 | 功能 |
|---|---|
| 空格 | 开局开始；开始后暂停/继续 |
| W / A / S / D | 上 / 左 / 下 / 右，大小写均可，不需要回车 |
| P | 暂停/继续 |
| + 或 = | 加快，每档减少 10 ms，最快 10 ms/step |
| - | 减慢，每档增加 10 ms，最慢 150 ms/step |
| Q | 输出 Quit.，退出码 0 |

地图内部为 12×8，`@` 是蛇头，`o` 是身体，`*` 是食物，边框为墙。
横向相邻格子之间插入一个空格，改善终端字符的宽高比；内部显示宽度为 23 个字符，
含左右边框共 25 个字符，逻辑地图仍为 12×8。
初始长度 3，向右移动，吃一份食物增加一节身体和一分。
撞墙或身体结束，填满 96 格获胜；结束显示最后棋盘，再调用 `system.Exit(0)`。
内核随后按当前双进程模型输出退出日志并停机。重新运行需复位。

初始为等待状态，不会在看清画面前自动撞墙。默认移动等待为 100 ms/step。
同一步之间只接受一次有效转向，禁止 180° 掉头；快速输入 W、A 不会让向右的蛇直接反向。
没有增长时允许蛇头进入该步恰好离开的旧蛇尾格。

## 为什么不只画蛇头和蛇尾

项目电路使用 Digital 的 Terminal。上游标准实现处理换行、删除和 `\f` 清屏，
没有 ANSI 光标定位；CR 也被当作换行，而非回到当前行开头。
因此不能靠发送 `ESC[y;xH` 或 `\r` 实现可靠的任意位置覆盖。
依据：[Digital TerminalDialog.java](https://github.com/hneemann/Digital/blob/master/src/main/java/de/neemann/digital/gui/components/terminal/TerminalDialog.java)。
若将来增加可寻址文本显存或真正支持光标定位的终端，才适合做蛇头/蛇尾脏格刷新。
本版不修改电路，不假设它具备这项能力。

当前优化分成四部分：

1. `system.io.buffer` 用全局 32 位字符缓冲，每满 64 字或帧结束时调用一次 `system.io.Write`。
   不再每个字符都执行 INT、完整寄存器保存恢复、IRET。
2. 内核验证整段地址后输出，省去 PutString 每字重复地址验证。单批最多 64 字，
   不把几百字的整帧锁在一个关闭中断的系统调用内。
3. 地图保持紧凑，只有移动、开始/暂停、调速、结束时刷新。空闲或等待按键不重复画屏。
4. 身体用环形数组保存，普通一步只更新头尾；占用表让碰撞判断无需扫描整条蛇。

默认等待开局画面为 **328 字、6 次 Write 调用**；五子棋的正常棋盘加提示为
**84 字、2 次 Write 调用**，此前为 65 次输出系统调用。数字来自宿主测试。
这不是宣称帧率提高 32 倍：终端仍需逐字符 MMIO，Digital GUI 仍逐字符更新，
用户态组帧、CPU 时钟、微码与调度同样影响速度。清屏重绘仍可能有闪烁。

## 时间、回调与共享状态

`system.TimeMs()` 通过系统调用 10，由内核读取 `0x08000000`，返回无符号毫秒数，
模 2^32。用户不能直接读取该内核设备。经过时间用无符号减法比较，处理正常计时回绕。

每次画面输出完成后记录时间，再等待当前档位的间隔。因此每步实际耗时约为
“设定等待 + 逻辑/画面输出时间”，而不是承诺严格固定帧率。慢速电路不会在绘图后
连续补执行多个不可见的移动步骤。+/- 也不会造成突然快进。
暂停/继续及速度变化后重新开始计时。

键盘回调只把 `0xA5SSSSCC` 事件放进 32 槽队列（有效容量 31），不绘图、不改游戏状态。
主循环验证签名、非零 16 位序号和重复事件后再解释按键，不调用 GetChar 轮询设备。
每次最多消费 32 个事件，避免持续输入饿死游戏更新。队列溢出时暂停，按 P 恢复。
内核回调禁止重入，硬件/内核层丢失的输入无法由此队列恢复；不承诺粘贴输入无损。

等待主循环会读取系统时间并执行少量 NOP；没有真正的 sleep/wait 系统调用，
不会擅自在用户态执行 HALT。tick 继续调度系统进程和用户进程。

可写字符缓冲采用 `aurora_word_t[]` 而非窄 char 存储。少量布尔状态显式 volatile，
避免当前编译器把静态 int 标志缩成后端暂不支持的 i8 存储。

## 偶发 Write 失败的诊断版本

实机曾在第一批 64 字输出结束处报错。旧提示 `Load matching kernel` 只是通用提示，
不能据此判定内核版本不匹配。相同提示还可能来自错误返回值或缓冲长度被破坏。
该故障后来在 Digital 引擎中复现并定位到 CU_INT 片选切换，见文末修复结论。

文本库现在在存入字符前检查长度，记录请求长度快照，不再把所有异常返回值都丢弃为 -1；
批量提交保持独立的小函数，避免检查逻辑复制到所有绘图循环，保留正常中断和调度。
失败仍退出，不自动重试，以免重复输出掩盖现场。会打印：

```text
Console Write failed: stage=... batch=... requested=... returned=... after=... error=... address=...
```

- `stage=1`：本地长度超过 64，尚未发起这次 Write。
- `stage=2`：Write 原始返回值与本次请求长度不符。
- `stage=3`：返回长度正确，但缓冲区 used 在调用前后不同。
- `stage=4`：追加一个字符后，立即读回的计数与预期不符。
- `batch`：该帧已发起的批次号；`after` 为返回后观察到的 used。
- `returned=-1/-3/-4` 分别对应内核 EINVAL/ENOSYS/EFAULT；非负但不等于请求长度也会报错。
- `address` 是缓冲区的 CPU 字地址，以有符号十进制显示；负值需按原始 32 位模式理解，
  不表示地址必然非法。

测试新增越界长度、异常返回值、调用期间长度改变、失败不重试，以及 1000 帧输出边界的
模拟键盘回调。它们只证明错误分支的记录和边界保护，不能验证硬件 IRQ 的寄存器/FLAGS 恢复。

## 开局蛇头分离：已定位的编译器错误（2026-10-17）

旧镜像可能在 0 分时把 `@` 显示在左上角，而三个 `o` 留在第 5 行；之后还可能出现
身体格数与分数不符、错误碰撞。这个开局问题已在旧 BIN 的指令级模型中复现，并非键盘操作造成。

Clang 在字节模型下把部分地址加法优化成 `or disjoint`。Aurora 后端随后把全局变量
替换为紧密分配的硬件字地址，这些地址的低位不一定满足原来的对齐假设。
在指令选择之前常量折叠已经把两个数组元素合并到了同一地址。
实际旧汇编把 `x[2]=6` 写到了 `x[0]`，也把 `y[2]=4` 写到了 `y[0]`；
真正的 `x[2]/y[2]` 保持 0，蛇头于是出现在 `(0,0)`。

修复位于 LLVM 后端 `AuroraTargetMachine.cpp` 的 `AuroraAllocateGlobalsPass`：
在全局地址替换前，把带 disjoint 标记的 OR 规范化为无额外溢出假设的加法；普通位 OR 不变。
之前仅在 SelectionDAG 指令选择时处理已经太晚。新 clang/llc/opt 已同步到 build-tools，
内核及五个用户目标已全部重建。请重新加载配套 ROM/UROM，不要只改 C 源码后继续用旧工具。

此前还用直接执行 `snake.bin` 的 ISA/ABI 模型进行了验证（测试脚本现已清理）：

旧 BIN 在开局即失败，并复现头身分离画面。新 BIN 通过 100 帧绕圈（1226 次编译后的用户回调），
以及 40 帧寻食到 7 分（498 次回调）；逐帧检查头身连通和蛇长等于分数加 3。
寻食规划器只是测试路径工具，不能保证任意长度测试都不会把自己围住；不是游戏里的自动模式。
模型模拟了用户指令、普通栈帧、系统调用 ABI 和理想回调恢复，不模拟 Digital 微码或真实 IRQ 时序。

此前 `stage=1 batch=0` 的巨大缓冲长度仍未独立复现，不能据这项修复断言所有偶发错误已消除。
新镜像保留错误快照；若再次出现 Write 错误，请保留完整 stage/batch/requested/returned/after 信息。

### 巨大计数问题的继续排查

实机仍报告 `stage=1 batch=0 requested=261030019`。这说明当前检查发现第一批提交前
计数已不合法，并不证明是 Write 系统调用返回错误。尚未在指令模型中复现，不能宣称已修复。
追加路径现在只使用已经检查过的局部下标写字符，不再重新加载一个未经检查的 volatile
计数作为数组下标。每次追加会记录并读回计数，失败时额外输出：

```text
Append: before=... expected=... observed=... char=...
```

这些值是最后一次追加的旧计数、预计新计数、立即读回值和字符码；不是发生故障的 PC。
若读回已经不符则 stage=4；若读回正常而后来 stage=1，则可进一步追查追加完成之后的破坏。
保留失败退出，不清零后继续，也不关闭 tick 或键盘回调来掩盖错误。

此前的联合测试直接执行内核和用户 BIN，实际运行调度、系统调用、回调准备及恢复代码（脚本现已清理）。

IRQ 按模型的指令计数周期注入，时间设备也采用模拟时间；不是电路实时毫秒或微码测试。
模型实现独立 KSP/KFP、USP/UFP，先进入内核再压 FLAGS/PC，IRET 先弹 PC 再恢复 FLAGS。
模型通过不能排除硬件时序、总线或模型未覆盖的问题。
当前 100/10/150 ms 版本联合测试通过 100 帧，执行 459 次 tick IRQ、272 次键盘 IRQ，
共 4,665,744 条指令；用户 BIN 独立测试通过 100 帧及 40 帧寻食（7 分）。

## 硬件故障修复与测试清理（2026-10-18）

排查最终定位到 CU_INT 的 ROM 片选与后级选择器同时由 INT_TAKE 切换：
选择器可能先选中尚处于高阻态的微码输出，导致控制信号毛刺及 URAM 随机写入。
修复是将 **CU_INT 的 SEL/CS 固定为 1**，保留 INT_TAKE 对后级选择器的控制。
用户已确认修改后正常运行，贪吃蛇成功运行到 12 分并暂停；不需要额外的 URAM WE delay。
这不代表所有硬件路径或任意运行时长都已验证。

临时的内存、寄存器、读写矩阵 probe、Digital 诊断驱动及产物已移除，
五子棋和内核 Write 的独立测试也不再放在贪吃蛇目录下。
当时保留的游戏测试和 BIN 模型已于 2026-10-19 随本轮用户目录整理一并清理。
历史测试按横向格间空格解析画面，逻辑坐标仍为 12×8。
