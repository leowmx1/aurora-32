# 内核事件队列、等待与主动让出

当前实现位于 `kernel/kernel.c`，适用于一个系统进程和一个用户进程。
事件不是消息线程，也不是嵌套 ISR：业务回调始终在用户态执行，可以被 tick 抢占。

## 数据流与所有权

键盘/Telnet ISR 保存 r0..r15，读取设备一次以应答，然后构造事件字：

- 键盘：`0xA5SSSSCC`。
- Telnet：`0xA6SSSSCC`。
- SSSS 是各来源自己的非零 16 位序号，允许回绕；CC 是设备字的低 8 位。

有订阅时，两种事件进入用户 PCB 的同一个 `events[64]` FIFO。read/write 相等表示空，
下一 write 等于 read 表示满，因此有效容量为 63 条。事件顺序是内核实际应答 IRQ 的顺序，
不是设备物理上产生输入的绝对时间顺序。内核不合并重复字符，不按序号去重。

满时丢弃新事件，保留已入队事件及其顺序，`event_drops` 模 2^32 累计。
它只统计订阅 FIFO 的软件溢出，不是硬件丢失计数，也不统计兼容 GetChar 队列的溢出。
示例通过 EventDrops 检测后停止，不能宣称任意输入速率无损。

`prepare_pending_event` 检查进程有效、非回调中、暂缓深度为零、当前有投递额度。
成功建立用户回调现场之后才前移读指针，一条事件只消费一次。
回调入口地址保存在 PCB 的各设备订阅字段，而不是由用户再从队列取字符。
替换或取消订阅会压缩 FIFO，移除该来源的旧事件，保持另一来源的先后顺序。
已在执行中的回调仍可以正常返回。

未订阅的键盘/Telnet 来源继续使用独立内核兼容字节队列，供非阻塞 GetChar/NEXT 读取。
订阅模式下 GetChar 返回 EBUSY，避免两个消费者竞争同一个事件。
图形已改回 Busy/Yield 轮询，不进入事件队列；详情见 [graphics.md](graphics.md)。

## 回调现场与返回

硬件/INT 先锁存原 FLAGS/P、切入内核，再在 KSP 压 FLAGS、PC。
软件再压 r0..r15，统一得到 18 字现场。入口在任何 C 调用前保存全部通用寄存器。
内核把被暂停用户现场保存到 PCB，并在回调 KSP bank 复制一个入口现场，替换 PC、r0；
PUSHU 向 USP 压普通 C 回调的返回跳板。C 函数可以普通 return。

跳板执行系统调用 7。内核重建原用户现场，恢复所有 GPR、PC、FLAGS；回调的普通 C
退栈已平衡 USP/UFP。专用 KSP 切换只在 C 帮助函数返回、其栈帧已退完以后执行。
系统调用保存的原请求号与返回结果分开，TimeMs 返回任意 32 位值都不会冒充回调返回。

`callback_active` 作用于所有来源，禁止同来源和跨来源回调重入。
回调里允许复杂计算、输出、普通函数调用、Yield；不能 WaitEvent 或 Sleep，否则会等待一个
不允许嵌套运行的回调，故返回 EBUSY。长回调会延后其他事件，仍可能填满有限队列。

## Yield、WaitEvent 与系统空闲

`system.Yield()`（请求 4）保存完整 syscall 现场，立即选系统进程，用户仍可运行。
它不是 sleep，不保证让出一个 tick 周期，也不承诺最小返回延迟。

系统进程启动完成后，如果用户有效且没有等待，主动通过 INT 请求 4。
调度器再次在 IE=0 的临界区检查可运行状态，保存系统现场并切用户。第一次启动也走
这一路径，所以首次进入用户不再依赖 tick。tick ISR 继续先应答设备，再进行正常调度。
系统的“无事可做”仅指当前启动后没有后台任务；未来加入后台任务，应先处理任务再主动让出。

用户 `WaitEvent()`（请求 15）在没有待投递事件/唤醒记号时标记 waiting，并切系统。
tick 会跳过 waiting 用户。系统空闲此时只执行可中断检查/NOP，不反复 INT、不唤醒用户，
也不使用会永久停止 CPU 的 HALT。新订阅事件入队时清除 waiting，允许投递回调，
系统空闲循环可立即 Yield 给用户，不必等待下一个 tick。

为避免“回调刚在 WaitEvent 前执行完，随后却永久睡眠”，事件到达还会留下合并的
`wake_pending` 记号。WaitEvent 可消费此记号立即返回；它不是每次等待下一次未来 IRQ，
也不表示返回时必有一个尚未处理的事件。推荐：检查业务条件，再循环 WaitEvent。
没有任何订阅时 EINVAL；正在回调或暂缓投递时 EBUSY。

回调返回不直接无限链接下一回调：恢复主循环，设置 cooldown，使下次系统→用户
调度留给前台执行；再后一次正常调度可投递新事件。WaitEvent 或最外层 ResumeEvents
表示前台明确允许投递，可以提前处理一条。Yield 后系统立即归还 CPU 不会跳过等待检查。
这是简单的防事件流独占措施，不是多用户进程公平调度算法。

## 共享状态保护

### 定时休眠 Sleep(ms)

`system.Sleep(ms)` 使用请求 29（r1=毫秒数，r2=r3=0），返回 `aurora_status_t`。

- `ms=0`：和 Yield 一样让出一次 CPU，不建立定时等待。
- `1..0x7fffffff`：记录起始毫秒数和等待长度，标记 waiting 后切到系统进程。
  无须订阅事件也可使用；没有订阅时只依靠超时恢复。
- 超时由现有 tick 调度检查；`timer` 提供毫秒计时，`tick` 提供唤醒机会，两者不是同一设备。
  使用无符号时间差处理 32 位 timer 回绕，不新增硬件中断/定时回调。
- 已订阅的键盘或 Telnet 事件可以提前结束等待，取消该次定时状态，调度用户回调。
  回调返回后继续 Sleep 后面的代码，不会自动补睡剩余时间。未订阅来源的兼容字节队列不唤醒 Sleep。
- 已有待投递事件或 wake_pending 时，不先睡下去；允许事件投递或消费记号直接返回。
  这覆盖 ResumeEvents 或 IRQ 在 Sleep 前刚刚运行完回调的竞态。
- 到期、事件提前唤醒以及 Sleep(0) 均返回 0，不区分唤醒原因；调用者重新检查业务状态与时间。
  参数超过 INT32_MAX（包括传入负数后的无符号值）或 r2/r3 非零返回 EINVAL。
  在用户回调或 DeferEvents 区内调用返回 EBUSY，即使 ms=0 也如此；此时可用 Yield。

Sleep 不是保证“至少睡满 ms”的标准库延时：订阅事件/记号可提前返回；超时唤醒也受 tick
间隔和 IRQ/调度耗时影响，可能晚于期限。若希望等待到业务期限，须每次重算剩余时间：

```c
aurora_word_t start = system.TimeMs();
for (;;) {
  // 在这里检查回调更新的退出/暂停/变速等状态，必要时结束或调整等待。
  aurora_word_t elapsed = system.TimeMs() - start;
  if (elapsed >= 100u) break;
  if (system.Sleep(100u - elapsed) != AURORA_OK) system.Exit(1);
}
```

这不是在用户态轮询度过整个间隔：每次 Sleep 都由内核阻塞，下一轮只在到期/事件后运行。
系统 idle 仍保持中断开启并检查/NOP，不执行硬件 HALT，因此这是进程休眠，不是 CPU 停钟省电。
Sleep 期间 tick 继续处理 MIDI 序列；退出/异常清除定时等待，WaitEvent 则不继承任何旧超时。

### 暂缓回调

`system.DeferEvents()` / `ResumeEvents()` 以可嵌套计数暂缓/恢复用户回调投递。
它们不改变硬件 IE：IRQ 继续入内核 FIFO，tick 照常抢占。最后一次 Resume 可在返回
调用者前投递一条事件。无匹配 Resume 返回 EINVAL，深度溢出也返回 EINVAL。

仅有非嵌套回调还不足以保证前台共享数据安全。若主循环和回调都写同一对象，必须用
成对暂缓保护，或把业务移入单一回调上下文。不能在暂缓区调用 WaitEvent/Sleep，也不要长时间
持有它。调用 Yield 不会自动解除暂缓状态。

计算器、五子棋、猜数字、迷宫和终端在回调里完成业务，前台只等待。
贪吃蛇回调处理键盘，前台保护游戏更新/绘图；运行时按下一步剩余时间 Sleep，暂停时 WaitEvent。
绘图完成仍用 Busy/Yield（无图形完成事件）；结束旋律每 20ms Sleep 后检查是否播放完毕。
本轮没有实现定时用户回调、多个用户进程、动态队列容量、优先级或硬件流控。

## 验证与加载

`tests/kernel-events/` 的回归直接执行新 kernel.bin 和 user.bin；不是替身实现调度器。
测试模型实现理想 ISA、banked 栈、硬件入栈和 IRET，不模拟 Digital 微码传播延迟。
覆盖 FIFO、溢出、取消订阅、暂缓、阻塞、无 tick 唤醒、回调内 Yield、全现场恢复及六个示例。
具体命令见同目录 README。编译检查同时拒绝用户特权指令、未解析符号和重定位。

内核变化后系统调用 ROM 地址会变，必须重新构建并加载一套匹配的 ROM/UROM。
软件模型通过不能替代电路验证，也无法修复设备中断未锁存、总线高阻或微码错误。
