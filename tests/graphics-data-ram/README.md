# 图形 data RAM：独立内核态 ROM 测试

仅把 `build/data_ram_test.hex` 加载到 **ROM**，复位从 PC=0 开始。
不用加载正式 kernel.hex、UROM 或 storage。启动首先初始化 KSP/KFP，然后 DI，
全程内核态，不注册 ISR、不启用 tick、不调用系统调用、不改正式内核或用户库。
本版要求 **480×240** 显存，GPU 地址为 `(y+局部Y)*480+x+局部X`。
X/宽度至少 9 位，线性显存地址至少 17 位；不要在旧 160×100 硬件上运行。

## 本测试采用的硬件协议

CPU 为字寻址，以下地址不乘 4。按最新硬件约定，图形段高 4 位 `[23:20]`
统一选择寄存器，低 20 位 `[19:0]` 是内部地址。普通寄存器只使用内部地址 0：

| 完整 CPU 字地址 | 用途 |
|---|---|
| 0x09000000 | x |
| 0x09100000 | y |
| 0x09200000 | w |
| 0x09300000 | h |
| 0x09400000 | 前景色 |
| 0x09500000 | 背景色 |
| 0x09600000 + n | Grdata RAM[n]，n 为低 20 位内部字地址 |
| 0x09700000 .. 0x097fffff | 原 datahigh 槽，空置；测试不写 |
| 0x09800000 | mode：0 矩形、1 双色位图、2 透明背景位图 |
| 0x09900000 | stat：写 0 停止，写 1 启动；忙时读非零，完成自动清零 |

不使用旧的单字 datalow 写法 `0x09000006`。例如，RAM[0]、RAM[1]、RAM[2]
分别写 `0x09600000`、`0x09600001`、`0x09600002`。
旧低四位寄存器地址（例如 `0x09000001`、`0x09000009`）不再使用。

位图按行优先连续打包，**每行不补齐到 32 位**：

```text
i = y_local * width + x_local
word = data_RAM[i / 32]
pixel_bit = (word >> (i % 32)) & 1
```

左上角为 RAM[0] 的 bit0；第 32 个像素为 RAM[0] 的 bit31，
第 33 个为 RAM[1] 的 bit0。每次绘制从 RAM[0] 重新开始。
mode 1 的 0 位写背景色，mode 2 的 0 位完全不写显存；mode 0 忽略位图。
程序只填本次位图需要的 RAM 字，不清空整个 20 位地址空间；最大文字条为
480×8、120 个数据字，另写一个尾部越界哨兵。
字母和诊断图已预先打包成常量数组，运行时直接逐字上传，不让 CPU 逐像素计算字形。

每次等 stat 空闲，再写参数和数据，最后写 stat=1；完成前不改参数、不改 data RAM。
timer `0x08000000` 提供模 2^32 毫秒时间；等待超过 10 秒输出任务号并空转，不继续写设备。
正常结束也只 NOP 空转，保留画面，不 HALT、不重复画图。

## 应看到什么

预期画面见 `build/preview.png`（2 倍最近邻放大）和 `build/preview-native.png`
（480×240 原生像素）。它们是理想模型参考图，不是电路运行截图。

- 顶部原生小字：**5×7 字形、6×8 字符格**，含大写、小写、数字和英文句子，不放大。
- 右上 (288,26) 为黑底白字，检查 X 的第 9 位以及反色文字。
- 中部在 (16,88) 画 **35×42 的红色 A，蓝色背景**。
- 绿/黄双色底板上在 (90,88) 画 **35×42 的黑色 F，透明背景**。
- 再用全零透明位图覆盖 F 所在矩形，画面应完全不变。
- 右半屏 (280,88) 为 4 倍放大的 **ABC**，同一字形对应 24×32 字符格。
- 下方红、绿、蓝、黄矩形带透明文字标签；蓝矩形横跨 X=255/256，黄色矩形位于右半屏。
- 左下 (16,202) 是 **65×17 黑白诊断图**：外框及 bit31/32 跨字位置标记。
- 右下有文字和独立绿色矩形，检验屏幕下部地址。
- y=228 放一整行 **80 个数字**，以一个 480×8 位图任务绘制，检查宽度第 9 位。
- 整屏四边均有单像素黑框；新屏幕最右下角 **(479,239)** 为单个红点。

A/F 每个大字母 1470 位，需要 46 个字，远大于原来的两个字。35 像素行宽使字边界
不断穿过不同行的位置，能发现固定 8 位行距、固定 64 位掩码或行尾错误补齐的问题。
最后一个字的未使用位和紧随其后的 RAM 字故意置 1；绘制必须在 w*h 处停止，
不能溢出矩形或污染邻近像素。透明空位图也含这些尾部哨兵，用于检查截断。

终端的 `Data RAM test DONE` 仅表示任务全部完成，不代表软件读回验证了显存；
实际图案仍需与参考图比较。最后边框用于检查切回 mode 0，不能受残留 RAM 影响。

## 构建与软件验证

从 `F:\aurora-32` 执行：

```powershell
.\build-tools\compile.ps1 tests/graphics-data-ram/data_ram_test.c tests/graphics-data-ram/build/data_ram_test.hex -Mode kernel
python tests/graphics-data-ram/run_data_ram.py --preview
```

`text_patterns.py` 保存可读的 5×7 字模和文字任务定义，`text_data.h` 是预先打包的
位图及任务表。`python tests/graphics-data-ram/text_patterns.py --header` 可输出对应头文件。
修改字模/文字后需要同步头文件再重编译；验证脚本会检查两者一致。

验证脚本执行真实 BIN，检查完整 **115200 像素**、全部任务参数、上传地址、31/32 位边界、
大于 64 位的图案、透明空位图、尾部裁剪、busy 等待、timer 回绕、超时不继续写入、
启动时设备已忙不强制取消，以及结束后不重画。还检查 X>255 的位图、480 像素宽位图、
边框和最后一个像素。设备是理想契约模型，**不是 Digital 时序仿真**。

旧的 `tests/graphics-bitmap` 测试保留，使用旧双寄存器协议，不适用于本次 data RAM 硬件。
正式内核和用户库已迁移到新地址和 480×240，新增 Image/ImageTransparent 数据指针接口。
该独立内核态测试仍可单独加载验证硬件，不经过系统调用；正式接口见 docs/kernel/graphics.md。
